Why Metadata-Driven? The Shift from Rule-Based
The previous rule-based approach hardcoded eligibility logic directly into code — meaning every new scheme, every policy update, or every new document required a developer to modify the application. The metadata-driven approach inverts this: schemes, eligibility criteria, and document requirements are stored as structured data (metadata), and the agent reads from that data at runtime.

What "Metadata" Means Here
Every scheme is described by a metadata record — a structured document (stored in Qdrant, Neo4j, and optionally a YAML/JSON config) that contains all the information the agent needs to reason about it. The agent never has hardcoded rules like "if income < 100000 and state == Maharashtra then eligible for PMAY". Instead, it reads the PMAY metadata record and evaluates the citizen profile against it dynamically.

Eligibility Evaluation — Runtime (No Hardcoding)
At runtime, the agent loads scheme metadata and evaluates the citizen profile against it using a generic rule engine. The same code evaluates every scheme — only the metadata changes.
# Generic rule evaluator — works for ALL schemes
def evaluate_eligibility(citizen_profile, scheme_metadata):
    results = []
    for rule in scheme_metadata["eligibility_rules"]:
        field_value = citizen_profile.get(rule["field"])
        result = apply_operator(
            field_value, rule["operator"], rule["value"]
        )
        results.append(result)
    
    if all(results):
        return "ELIGIBLE"
    elif sum(results) / len(results) > 0.7:
        return "LIKELY_ELIGIBLE"
    else:
        return "NOT_ELIGIBLE"
