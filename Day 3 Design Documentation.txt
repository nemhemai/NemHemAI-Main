2. DESIGN PRINCIPLE

Persistence follows structure-first architecture:

Structured JSON remains the single source of truth.

Storage layers consume structured output without modifying schema.

Rules enforced:

• Extraction owns structure.
• Backend owns identity generation.
• Graph layer consumes structure.
• Retrieval (future) will not alter identity fields.

4. PERSISTENCE LAYERS IMPLEMENTED

4.1 Graph Persistence (PRIMARY)

Purpose:
Store legal structural relationships safely and atomically.

Data Stored:

• Act nodes
• Section nodes
• Act → Section relationships

Neo4j Responsibilities:

✔ Represent hierarchy
✔ Maintain structural relationships
✔ Enforce uniqueness constraints
✔ Prevent duplicate insertion
✔ Ensure atomic transactions

Graph does NOT store embeddings.

---

4.2 Chunk Preparation Layer (PRE-EMBEDDING)

Purpose:
Prepare section content for future semantic indexing.

Responsibilities:

• Split section content into overlapping chunks
• Preserve act_id and section_id
• Generate deterministic chunk_id
• Maintain metadata integrity
• No database writes
• No embedding generation

Chunking logic was stabilized to prevent infinite loop and memory errors.

---

5. DATA CONTRACT (IMPLEMENTED)

Structured JSON format:

{
  act_id,
  act_title,
  sections: [
    {
      section_number,
      heading,
      content,
      clauses,
      section_id
    }
  ]
}

Enforced Rules:

• IDs are generated deterministically using backend utilities
• No schema modification during persistence
• section_id remains consistent across layers

---

6. GRAPH INGESTION IMPLEMENTATION

Nodes:

Act:
• act_id (Unique)
• name

Section:
• section_id (Unique)
• act_id
• title
• content

Relationships:

(:Act)-[:HAS_SECTION]->(:Section)

Insertion Strategy Implemented:

• MERGE-based upserts
• Unique constraints on act_id and section_id
• Single-transaction ingestion
• Full rollback on failure
• Idempotent re-ingestion verified
